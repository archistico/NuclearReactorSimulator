## Goal

Convert the feature-complete validated simulator into a reproducible release candidate. M11 is not a feature milestone.

## M11 rule

No new physics, gameplay feature, challenge type, control-room feature or accident model is added in M11 unless a release gate proves a blocking defect that cannot be fixed within an existing owner.

## Release evidence philosophy

M11 must answer five questions:

1. what exact product/version do we support?
2. which existing saves/scenarios/sessions do we promise to read correctly?
3. does it remain performant and memory-stable during realistic use?
4. can a clean supported machine install/start/use/save/reload it?
5. do the executable, manual, README and known-limitations statement all describe the same product?


### Pre-M11 review-derived release contracts

M11 also adopts the following assurance contracts without adding product features:

- the final M10 27-row phenomenon V&V matrix is retained as release provenance;
- verification, model-assessment evidence, integral qualification and HMI acceptance remain distinct claim classes;
- Digital-I&C architecture invariants are frozen and machine-checkable where practical;
- Human–Automation Function Allocation is explicit and may not drift silently during release hardening;
- deterministic Digital-I&C hazards are reviewed through positive evidence or explicit limitation/non-claim;
- classic HMI failure modes (data overload, keyhole effect, mode error, clumsy/opaque automation) are part of release acceptance;
- desktop timing is characterized as soft-real-time wall-clock responsiveness while 10 ms logical time remains the sole simulation-semantic authority;
- runtime/COTS dependency assurance is proportional to role and support significance; no nuclear-grade COTS qualification is claimed.

- supported OS targets;

- minimum display/window expectation;

### Deliverables

## M11.2 — Save/scenario/session compatibility and migration hardening

### Compatibility inventory

Build a matrix across:

- current production exact-v4 desktop profile/session;
- historical exact identities explicitly promised;
- current scenario schema versions;
- session archive schema v1;
- checkpoint versions;
- post-incident persisted formats where user-facing;
- unknown future schema behavior.

### Required behaviors

- old supported input reads without semantic reinterpretation;
- unsupported old input fails with a precise migration/support message;
- future schema fails closed with `NotSupportedException`-equivalent public behavior;
- no opaque state dump becomes authoritative;
- exact-version identity remains immutable.

### Session archive schema v2 decision

Schema v1 currently freezes numeric enum ordinals. The **default M11 decision is to retain v1** unless a concrete release blocker proves that a versioned v2 migration is necessary. Cosmetic cleanup alone is not sufficient reason to introduce a release-format migration.

If **no**:

- document v1 as release format;
- retain ordinal freeze tests;
- keep additive compatible fields only where allowed.

If **yes**:

- define v2 schema contract;
- prefer string enum representation only as an explicit versioned change;
- preserve v1 reader/migration path;
- prove v1→current replay equivalence for supported cases;
- never silently emit v2 while labelling it v1.

### Snapshot fingerprint algorithm compatibility

M10.9.7.4 freezes a populated golden anchor for `sha256-control-room-snapshot-v1`. M11 keeps v1 as the default release algorithm; fingerprint v2 is not introduced unless a concrete compatibility requirement justifies it. If a future fingerprint v2 is introduced during/after release hardening:

- persisted recordings/checkpoints must declare the fingerprint algorithm they require;
- replay/seek selects the declared supported algorithm instead of assuming only the current implementation;
- supported v1 expected hashes remain immutable;
- unsupported algorithm ids fail closed with a precise compatibility error;
- migration must not rewrite historical v1 hashes as though they had been generated by v2.

### Recording-contract versioning

M9.1 recording v1 remains one contiguous fingerprinted frame per logical step. Any future decimation, prefix truncation, circular buffering or other retention semantic requires an explicitly versioned recording/archive contract and compatibility evidence.

### Additional Digital-I&C compatibility checks

Supported persisted evidence must also preserve, where those concepts are part of the versioned contract:

- logical-step/action ordering;
- requested/effective authority semantics;
- automation objective/intent ordering;
- protection-state semantics;
- measured/provenance semantics;
- declared fingerprint algorithm identity.

A replay route that structurally deserializes but reconstructs different authority/protection/history is a compatibility failure. Add an action/history consistency sentinel to the executable matrix.

### Gate

Compatibility matrix must be executable and artifact-backed.

## M11.3 — Performance, memory and long-run release budgets

### Measure before optimizing

Freeze release budgets from current validated behavior and release-representative hardware.

Measure at least:

- 10 ms simulation-step throughput;
- median/p95/**worst observed** desktop runtime-batch duration;
- representative input-to-visible-response latency where measurable;
- HMI snapshot publication/update cost;
- mission/computer/mimic rendering update cost where material;
- managed allocations per bounded run;
- gen0/gen1/gen2 collection behavior;
- memory growth over long soak;
- repeated session load/reset/save cycles;
- save/checkpoint/session JSON size;
- save/load wall cost;
- Large Object Heap evidence;
- startup to usable control room;
- workspace-switch responsiveness where material.

### Persistence streaming decision

Evaluate `Stream`/`Utf8JsonWriter` or equivalent only if measurements show material allocation/LOH pressure.

If adopted:

- preserve deterministic JSON/schema semantics;
- add stream-based Application ports deliberately;
- keep string helpers only as compatibility/test convenience if appropriate;
- measure before/after;
- prove no replay/session behavior change.

### Simulation hot-path candidates from the post-7.3 review

These are **measurement-first, physics-preserving** candidates. M11.3 may optimize them only if before/after evidence shows material value and exact representative outputs remain equivalent.

1. **Pump/valve effective-resistance plumbing** — avoid constructing/revalidating a temporary `PipeDefinition` merely to pass an effective resistance into `PipeFlowSolver`; prefer an internal override-resistance seam while preserving canonical endpoints, sign and energy-transport mode.
2. **Four-node trigger-path allocations** — measure branch-continuity/corrector/list/set construction on actual correction triggers. Reuse is allowed only with explicit clear/reset semantics and exact deterministic-repeat evidence.
3. **Expected infeasible probe control flow** — measure throw/catch frequency/cost for infeasible Newton/Anderson probes. A `TryResolve`-style seam is allowed only if unsupported-state and programming-contract failures remain distinguishable.
4. **Thermodynamic root-search ceilings** — measure coarse-search and bisection iteration distributions, especially near phase boundaries; do not reduce work if root set/selection/fingerprints change.
5. **Generic runtime catch-up API** — inventory supported callers of `SimulationRuntime.Advance(elapsed)`. The desktop host already uses five-step cooperative batches under `ControlRoomRuntimeCoordinator` limits; any generic cap/backlog/drop policy must be explicit and must never silently discard deterministic simulation time.
6. **Deterministic summation cost/error evidence** — compare the current signed ordering + compensated sum with alternatives only in a diagnostic harness. A trajectory-changing summation convention is **not** an M11 optimization and routes to M12.2.

The near-zero quadratic hydraulic law, ideal check-valve non-smoothness, valve near-close constitutive changes, Jacobian conditioning-policy changes and pump loss-to-heat physics are explicitly **not M11.3 optimization scope**. They belong to M12.2/M12.4.

### Application recorder/fingerprint candidates from the post-7.3 review

Measure before changing semantics:

1. **Snapshot fingerprint cost** — normalized snapshot construction, JSON-to-UTF8 serialization, SHA-256 and hex formatting/allocation at full-step recording cadence. `Convert.ToHexStringLower` or equivalent is allowed only if the v1 golden fingerprint remains exact.
2. **Recorder collection views** — replace `Frames`/`Events`/`Checkpoints` property-wide copies with stable non-copying read-only views if measurements or API-hardening justify it; mutation ownership remains private.
3. **Lifecycle notification cost** — measure per-step `LifecycleChanged` subscribers and distinguish performance cost from semantics. A future split into sampled/outcome/transition notifications is a behavioral contract change, not a cleanup.
4. **Long-session recording growth** — measure frame/string/object growth, GC/LOH behavior and archive size for hour-scale sessions. Optimize storage/streaming/chunking without silently dropping v1 frames.
5. **Recorder evidence-failure policy** — decide explicitly whether evidence-production failure faults the host or transitions the recorder to a compromised/faulted state while plant execution continues. Any continue mode must make completion/save fail clearly and must never present an incomplete trace as authoritative.

### Desktop host / Avalonia presentation candidates from the post-7.3 App review

These are measurement/architecture items **after** the correctness-only M10.9.7.3 Hotfix 2. Do not use M11.3 to re-open already-fixed atomic-save/failure-containment behavior.

1. **UI-thread runtime batch cost** — measure `DesktopControlRoomRuntimePump.Tick()` end-to-end, deterministic batch duration and UI input/render latency. Current `DispatcherTimer` callbacks do not overlap concurrently; the risk is synchronous UI-thread occupation and slowed presentation cadence.
2. **Projection/publication cost** — measure mimic/schematic/COMPUTER/MISSION projection cost at presentation cadence and identify expensive unchanged work.
3. **PropertyChanged fan-out** — quantify the large unconditional `MainWindowViewModel.OnSnapshotChanged()` notification surface and binding reevaluation cost before changing notification semantics.
4. **Worker ownership study** — if measurements justify background execution, first define one runtime owner and immutable snapshot handoff to Avalonia. Opportunistic `Task.Run` around mutable session/runtime code is forbidden.
5. **Archive export responsiveness** — after picker-before-export correctness is established, measure long-session serialization cost. Off-thread serialization is allowed only from an immutable captured archive/recording representation with deterministic ownership.
6. **Desktop pacing contract** — document/measure the current fixed steps-per-timer-callback policy. A user-facing simulation-speed feature is not an implicit release optimization and requires separate product approval.

Structural decomposition of `MainWindowViewModel` and stable-ID operator-selection semantics belong to M13 rather than M11.3.

### Other maintenance candidates

Scenario-definition double parsing and comparer normalization may be addressed here only if they are measurable or improve release reliability without semantic risk.

### Digital-I&C timing/evidence requirements

- no host/runtime policy may silently drop deterministic simulation time;
- wall-clock responsiveness is characterized, not promoted to simulation authority;
- any background-worker proposal requires one explicit runtime owner plus immutable version/logical-step handoff;
- recorder/evidence failure policy must be explicit before release: either fail the relevant host/session path or mark recording **COMPROMISED** and block authoritative completion/save; silent partial evidence is forbidden.

### Gate

No optimization may weaken physics, conservation, replay, protection or determinism contracts.

## M11.4 — Packaging, publish and deployment verification

### Per supported target

- clean restore/publish;
- verify runtime/native dependencies;
- verify Avalonia assets/fonts/resources;
- exclude test projects, evidence payloads, dev docs if not intended;
- verify writable data/log/session directories;
- launch on clean representative environment;
- run/pause;
- execute representative command;
- navigate core workspaces/COMPUTER/MISSION;
- save session;
- close/relaunch;
- load/replay session;
- verify known default configuration.

### Dependency assurance

For every supported target, verify the frozen direct runtime dependency matrix (.NET/Avalonia/native/assets) against the packaged artifact. Test-only infrastructure remains identified separately. A lightweight deterministic SBOM/dependency export may be added if low-risk; it is not a release blocker unless the support contract makes it one.

### Packaging contract

Define:

- folder structure;
- executable name;
- config location;
- user-data location;
- log retention/default behavior;
- session file extension/association only if deliberately supported;
- update/replace policy;
- uninstall/manual cleanup expectations.

### Failure discipline

A target that does not pass is removed from the support statement rather than labelled “probably supported”.

## M11.5 — Documentation and manual release alignment

### User-facing

- Italian manual matches UI labels exactly;
- installation/startup instructions match the packaged release;
- save/load/replay instructions tested on packaged build;
- procedures/training modes accurately described;
- minimum-window/keyboard instructions accurate;
- no internal milestone jargon in normal user content.

### Technical/public

- README contains concise install/run/use/support information;
- `KNOWN_MODEL_LIMITATIONS.md` lists genuine unresolved fidelity limits;
- release notes distinguish new functionality, fixes, known limits and compatibility;
- educational/reduced-order nature is explicit;
- no industrial safety/licensing claim.

### Digital-I&C / human-system release alignment

Publish and freeze:

- Digital-I&C architecture invariants;
- Human–Automation Function Allocation;
- deterministic Digital-I&C Hazard Catalog;
- HMI Classic Failure Modes Checklist;
- runtime/COTS dependency assurance statement;
- explicit limitations/non-claims for hard-real-time behavior, safety-grade redundancy/diversity and unmodeled communication staleness/delay/loss.

The HMI checklist must cover data overload, keyhole effect, mode errors, workload transfer/clumsy automation, opaque “strong and silent” automation, protection/authority visibility, signal quality/provenance and ACK/reset/protection-reset separation.

### Internal provenance and documentation-integrity gate

ADRs/history remain available but are not copied into the user manual. Before release, documentation integrity is checked mechanically:

- every live relative Markdown link resolves;
- every top-level `docs/*.md` file is present in [`TOP_LEVEL_DOCUMENT_INDEX.md`](../TOP_LEVEL_DOCUMENT_INDEX.md);
- ADR numbering is unique/contiguous for the retained sequence;
- every ADR exposes `## Status` and appears in [`adr/README.md`](../adr/README.md);
- `ROADMAP.md` contains future work only and no concrete active/validated checkpoint duplication;
- `ARCHITECTURE.md` remains subsystem/ownership oriented and contains no candidate-status narrative;
- source XML comments that describe architectural ownership are sampled against the stable docs, including the historical `ThermodynamicBranchContinuityModel` “shadow-only” wording, and stale ownership comments are corrected without changing runtime behavior;
- acceptance checklists are discoverable through the exhaustive index/owning milestone rather than appended ad hoc to the curated README.

The release gate should fail when a new live top-level document or ADR bypasses its required index.

### Exit condition

M11 closes only when a reproducible release artifact, validated source baseline, compatibility statement, supported-target statement, current manual and known-limitations document all agree.

After M11 is explicitly closed, the approved post-release expansion sequence starts at **M12 — Extreme Operations Foundations**.

## Explicit non-scope

M11 also does not implement a general operating-point equilibrium trimmer or retune production seeds. Reusable equilibrium/stability tooling is planned as M12.0; only a blocker-resolution diagnostic subset may have been completed before M10 closure.

Deferred until after release hardening:

- physical removal of historical numerical modes;
- M12 extreme-envelope/directionality, decay-heat and integrity foundations;
- M13 major control-room experience work;
- M14 spatial 2D core expansion;
- M15 fire/rupture/core-damage and other explicit consequence progression;
- multi-monitor support.
