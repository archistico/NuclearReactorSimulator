# M11 — Release Hardening — PLAN

**Status:** PLANNED — prerequisite M10.9.8 / M10 complete.

## Goal

Convert the feature-complete validated simulator into a reproducible release candidate. M11 is not a feature milestone.

## M11 rule

No new physics, gameplay feature, challenge type, control-room feature or accident model is added in M11 unless a release gate proves a blocking defect that cannot be fixed within an existing owner.

## M11.1 — Release/support contract and version freeze

Before packaging work:

- freeze release version identity;
- declare supported deployment target(s) explicitly;
- declare minimum/runtime prerequisites;
- freeze authoritative production scenario/exact-version identities;
- freeze save/session/replay compatibility policy;
- define release-blocker severity classes.

**Open decision:** supported OS/runtime deployment targets must be explicitly chosen here. Avalonia cross-platform capability alone is not a support promise.

## M11.2 — Save/scenario/session compatibility and migration hardening

Validate:

- current @4 desktop sessions;
- historical @2/@3 exact identities where support is promised;
- synchronization exact-family identities where support is promised;
- M10.7 session package schema/version handling;
- checkpoint/replay reconstruction;
- unsupported/unknown future schema fails closed with a useful error;
- no silent reinterpretation of historical exact versions.

If migration is required, it must be explicit, versioned and testable. Opaque private-state serialization remains prohibited.

The schema-v1 session archive currently freezes numeric enum ordinals. If the release compatibility policy chooses string-enum persistence, it must be introduced here as an explicit schema-v2 migration with v1 readability tests; it must not be silently retrofitted into schema v1.

## M11.3 — Performance, memory and long-run release budgets

Freeze release budgets from validated evidence rather than inventing arbitrary thresholds.

Measure at least:

- deterministic step throughput under normal operation;
- HMI publication/update cost;
- managed allocations and GC over bounded long soak;
- memory growth across repeated session reset/load cycles;
- save/checkpoint creation and restore cost where material;
- startup/load-to-control-room responsiveness where material.

A release optimization may not weaken numerical, replay, conservation or protection contracts.

Stream-based session/scenario persistence (`Stream`, `Utf8JsonWriter` or equivalent) is evaluated here only if measured save/load allocations, LOH pressure or repeated-load memory evidence justify it. The current string-based port is not changed speculatively.

## M11.4 — Packaging, publish and deployment verification

For each declared supported deployment target:

- produce the intended publish artifact;
- verify required runtime/config/assets are present;
- exclude test/evidence/dev-only payloads;
- verify first launch on a clean environment representative of the support contract;
- verify creation/use of writable user data/log/session locations;
- verify basic launch → run → pause → command → save/session → reload flow;
- document install/start/uninstall/update expectations.

Do not claim support for a target that has not passed this gate.

## M11.5 — Documentation and manual release alignment

Final documentation pass:

- Italian user manual is beginner-accurate, operator-facing and contains no source-code dependency;
- UI labels/screens/procedures match the release build;
- `PROJECT.md` becomes the release checkpoint;
- `KNOWN_MODEL_LIMITATIONS.md` contains only genuine unresolved limitations;
- README contains install/run/use/support-scope information appropriate to the release;
- architecture/ADR/history remain technical provenance rather than user-manual material;
- release notes clearly distinguish educational fidelity from industrial/licensing use.

## M11.6 — Release-candidate final gate

Run from a clean source/package state:

1. restore/build warnings-as-errors;
2. complete ordinary suite;
3. designated long/replay/reference regression pack;
4. clean published-artifact smoke test on every declared supported target;
5. save/session/replay compatibility gate;
6. performance/memory release gate;
7. final manual control-room checklist;
8. documentation/link/package-content audit.

A green M11.6 produces the release baseline. Any failure fixes only the demonstrated release blocker and reruns the affected gate plus the final release gate.

## Explicit non-scope

Deferred until after release hardening:

- physical removal of historical numerical modes;
- M12 extreme-envelope/directionality, decay-heat and integrity foundations;
- M13 major control-room experience work;
- M14 spatial 2D core expansion;
- M15 fire/rupture/core-damage and other explicit consequence progression;
- multi-monitor support.

## Exit condition

M11 closes only when a reproducible release artifact, validated source baseline, compatibility statement, supported-target statement, current manual and known-limitations document all agree.

After M11 is explicitly closed, the approved post-release expansion sequence starts at **M12 — Extreme Operations Foundations**. See `ROADMAP.md` and `milestones/M12.md` through `milestones/M15.md`.
