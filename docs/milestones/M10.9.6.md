# M10.9.6 — Operational Challenge & Energy-Demand Framework — PLAN

**Status:** ACTIVE — M10.9.6.1, M10.9.6.2 Hotfix 1 and M10.9.6.3 Hotfix 1 VALIDATED; M10.9.6.4 initial challenge-pack candidate.

## Goal

Add deterministic training objectives, external electrical-demand references and multidimensional evaluation without allowing challenge/scoring state to control the plant.

## Core semantic separation

The following must never be conflated:

```text
EXTERNAL GRID DEMAND / CHALLENGE TARGET
        ≠
GENERATOR REQUESTED LOAD / OPERATOR CONTROL SETPOINT
        ≠
ACTUAL ELECTRICAL OUTPUT
```

External demand is a scenario/training reference. It does not directly torque the generator, change the grid model or mutate the governor.

## M10.9.6.1 — Challenge lifecycle and logical-time contract

**Validated contract:** introduce versioned Application-layer challenge definitions and a read-only evidence tracker. Lifecycle is `NotStarted -> Ready -> Active -> Completed|Failed|Cancelled`; all timing uses logical simulation steps. Target windows are observational, while failure by time requires an explicitly authored hard deadline. Challenge conditions evaluate immutable snapshots plus accepted operator-action history only. The tracker receives no command dispatcher or plant-control-authority seam. Scoring policy is represented only by a stable identity in 6.1; no arithmetic is implemented before 6.3.

Technical reference: [`../OPERATIONAL_CHALLENGE_LIFECYCLE.md`](../OPERATIONAL_CHALLENGE_LIFECYCLE.md).

**Validation note:** the first M10.9.6.1 build was blocked only by two xUnit2013 collection-size assertions in the new test. Hotfix 1 replaces them with `Assert.Single`; no lifecycle/runtime contract changes.

### Deliverables

Freeze a deterministic challenge lifecycle with explicit semantics for:

- not started / ready;
- active;
- completed;
- failed when the challenge definition has a defensible failure condition;
- cancelled/reset by explicit session lifecycle, not by presentation navigation.

Each challenge definition must own:

- objective text/identifier;
- activation condition;
- target/required observations;
- logical-time start and optional target time/window;
- completion conditions;
- failure conditions only when evidence-based;
- challenge-specific allowed assistance/scoring policy.

### Acceptance

- no wall-clock dependence;
- publication stride cannot change transitions;
- same exact challenge/scenario identity + same logical/action trace → same challenge-transition fingerprint;
- lifecycle failure conditions are definition-owned; if declared failure and completion are simultaneous, failure wins deterministically;
- target windows alone do not fail a challenge; only an explicit hard deadline may do so;
- explicit cancel/reset are lifecycle calls, never presentation-navigation side effects;
- save/checkpoint/replay can reconstruct challenge state from versioned deterministic evidence; full recorder integration closes in M10.9.6.5;
- challenge tracking receives read-only evidence and cannot issue plant commands.

**Validation:** M10.9.6.1 Hotfix 1 passed build, complete ordinary tests and `scripts/run-m1096-challenge-lifecycle-audit.cmd` on 2026-08-20. The lifecycle/logical-time contract is frozen for M10.9.6.2.

## M10.9.6.2 — Deterministic external energy-demand profiles

**Validated contract:** optional versioned demand profiles are owned by `ChallengeDefinition` and evaluated only from logical-step offset after challenge activation. Profiles are bounded ordered control points using `HOLD` / `LINEAR` interpolation, supporting constant, step, bounded-ramp and piecewise sequences. `ScenarioChallengeExternalDemandProjector` publishes demand/request/output/error evidence without mutating any plant owner. Demand is unavailable without an owned profile or before activation; exposure of the next scheduled control point is definition-owned.

Technical reference: [`../OPERATIONAL_CHALLENGE_ENERGY_DEMAND.md`](../OPERATIONAL_CHALLENGE_ENERGY_DEMAND.md).

**Validation:** M10.9.6.2 Hotfix 1 passed build, complete ordinary tests and `scripts/run-m1096-external-energy-demand-audit.cmd` on 2026-08-20. The first build had stopped only on one CS0173 nullable-inference issue; Hotfix 1 changed that local to `double?` without changing the external-demand contract.

### Deliverables

Introduce versioned deterministic demand profiles suitable for training. Initial profile primitives should remain simple and auditable:

- constant target;
- step change;
- bounded ramp;
- piecewise sequence of constant/ramp segments.

Demand profiles use logical simulation time and publish:

- current external demand;
- next scheduled change when appropriate for the exercise;
- current demand/output error as presentation/evaluation evidence.

### Acceptance

- profile identity is versioned with the exercise/scenario contract;
- demand is unavailable outside exercises that actually own one;
- demand profile never changes generator requested load automatically;
- replay/checkpoint reproduces exactly the same demand timeline.

## M10.9.6.3 — Multidimensional evaluation and scoring contract

**Validated contract:** scoring is pure Application-layer observational arithmetic over versioned policies and authored dimension evidence. The first build compiled production code and failed only because the focused test omitted the parent `Scenarios.Challenges` namespace; Hotfix 1 added that single test `using` with no scoring-contract change and subsequently passed build, ordinary tests and focused audit. Standard exact v1 policies are `general-operations@1` = safety 45 / procedure 30 / stability 20 / logical-time 5 and `demand-following@1` = safety 40 / procedure 25 / stability 15 / demand 15 / logical-time 5. Pass/proficient/excellent thresholds are 60/75/90%. Critical safety and procedure failures are definition/evidence-owned dominance signals capped at 39% and 59% respectively; safety wins if both occur. Missing required evidence makes evaluation incomplete/non-passing. Standard guidance and authority modifiers are explicitly neutral 1.00.

Technical reference: [`../OPERATIONAL_CHALLENGE_SCORING.md`](../OPERATIONAL_CHALLENGE_SCORING.md).

### Required dimensions

The first scoring contract should separate at least:

- **SAFETY / PROTECTION DISCIPLINE**;
- **PROCEDURE / REQUIRED ACTIONS**;
- **STABILITY / OPERATING QUALITY**;
- **DEMAND TRACKING** when an energy-demand profile exists;
- **LOGICAL TIME / COMPLETION EFFICIENCY** where the exercise has a time objective.

### Dominance rule

Safety and procedure are dominant dimensions. Good demand tracking or speed must not compensate for an unsafe/prohibited action or a challenge-defined critical procedural failure.

Exact v1 weights/caps are frozen by the validated M10.9.6.3 contract above and may change only through a new policy version. They never emerge from UI code.

### Acceptance

- score is observational and deterministic;
- score cannot change plant/controller/protection state;
- every penalty/reward has a documented evidence source;
- unavailable evidence cannot silently score as success;
- assistance mode and plant-control authority remain separate dimensions and their scoring effects, if any, are explicit.

## M10.9.6.4 — Initial challenge packs

**Active candidate contract:** compose six versioned Application-layer challenge packs exclusively from existing validated scenario/check/fault owners. The catalog is `pre-start-circulation-preparation@1`, `synchronization-initial-loading@1`, `bounded-demand-following-5-10-5@1`, `post-load-change-stabilization@1`, `controlled-normal-shutdown@1` and `generator-trip-load-rejection-recovery@1`.

Each pack binds one existing scenario/objective, one challenge definition, one read-only condition evaluator, one exact M10.9.6.3 scoring policy and one documented evidence-source binding for every policy dimension. M10.9.6.4 performs no score arithmetic.

Demand schedule visibility is now settled: only `bounded-demand-following-5-10-5@1` exposes the next scheduled change; post-load-change stabilization exposes current demand only; synchronization owns no demand profile. Demand never mutates generator requested load.

`StandardOperationalChallengeConditionEvaluator` reuses M7.2 pre-start, M7.5 synchronization and M7.6 manoeuvring checklist evidence plus committed M8.4 generator-trip fault state and accepted operator-action history. It owns no dispatcher, runtime engine, controller, protection mutator or wall-clock seam.

Normal-operation challenge failure remains definition-owned: unexpected trips may fail the normal pre-start/synchronization/demand/stabilization challenges and accepted emergency actions may fail the normal-shutdown procedure. Conversely the generator trip is required evidence, not failure, in the load-rejection response challenge. No global trip=failure rule exists.

No hard failure deadline is authored in the initial pack; target windows remain observational until concrete runtime qualification in M10.9.6.5.

Technical reference: [`../OPERATIONAL_CHALLENGE_PACKS.md`](../OPERATIONAL_CHALLENGE_PACKS.md).

### Acceptance

- six exact pack identities resolve existing scenario objectives;
- every pack has exact scoring-policy identity and exactly one evidence binding per policy dimension;
- demand-profile ownership implies a demand-tracking scoring dimension, and challenges without demand profiles cannot use one;
- every authored condition is supported fail-closed by the read-only evaluator;
- generator-trip/load-rejection preserves challenge-specific trip semantics;
- no new scenario fault, physical behavior or plant command authority is added.

### Non-rule

Do not add a new physical fault merely because a challenge would be more interesting with one. Missing physics goes to the post-M11 backlog.

## M10.9.6.5 — Replay/checkpoint/determinism and closure

### Automated gate

- same seed/action trace reproduces challenge timeline, demand timeline and score exactly;
- checkpoint continuation matches uninterrupted execution;
- assistance-mode change does not alter physical plant state by itself;
- demand never becomes generator load command implicitly;
- protection remains authoritative over challenge success;
- challenge reset/session reset semantics are explicit and deterministic.

### Manual gate

- objective and current demand are understandable;
- demand/requested-load/actual-output are visually distinguishable;
- score decomposition explains why points were gained/lost;
- a protection event cannot look like a successful demand-following result merely because MW error is small.

## Decisions settled for M10.9.6.4

1. only the bounded 5→10→5 MWe demand-following exercise exposes the future demand schedule; post-load-change stabilization exposes current demand only; synchronization owns no demand profile;
2. concrete pack conditions reuse M7.2/M7.5/M7.6 checklist evidence and M8.4 committed fault/action evidence; the only explicit stable-load bands are the already validated 5 MWe (4.5–5.5) and 10 MWe (9.5–10.5) operating bands with 2980–3020 rpm synchronous-speed evidence;
3. no hard failure deadline is authored before M10.9.6.5 runtime qualification.

Settled in M10.9.6.3: weights/caps/grade scale are versioned policy-owned; protection-trip classification remains challenge-definition-owned rather than global; standard v1 assistance and plant-authority score modifiers are explicitly neutral 1.00.

## Explicit non-scope

- physical grid dispatch/load coupling driven by the challenge owner;
- new supervisory automation authority;
- severe-accident/damage scoring;
- wall-clock speedrun logic;
- presentation-side scoring calculations.

## Exit condition

M10.9.6 becomes VALIDATED only after build, ordinary suite, focused deterministic challenge/demand/scoring gate and manual exercise confirmation. Only then start M10.9.7.
