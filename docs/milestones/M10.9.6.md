# M10.9.6 — Operational Challenge & Energy-Demand Framework — PLAN

**Status:** PLANNED — prerequisite M10.9.5 VALIDATED.

## Goal

Add deterministic training objectives, external electrical-demand references and multidimensional evaluation without allowing challenge/scoring state to control the plant.

## Core semantic separation

The following must never be conflated:

```text
EXTERNAL GRID DEMAND / CHALLENGE TARGET
        ≠
GENERATOR REQUESTED LOAD / OPERATOR CONTROL SETPOINT
        ≠
ACTUAL ELECTRICAL OUTPUT
```

External demand is a scenario/training reference. It does not directly torque the generator, change the grid model or mutate the governor.

## M10.9.6.1 — Challenge lifecycle and logical-time contract

### Deliverables

Freeze a deterministic challenge lifecycle with explicit semantics for:

- not started / ready;
- active;
- completed;
- failed when the challenge definition has a defensible failure condition;
- cancelled/reset by explicit session lifecycle, not by presentation navigation.

Each challenge definition must own:

- objective text/identifier;
- activation condition;
- target/required observations;
- logical-time start and optional target time/window;
- completion conditions;
- failure conditions only when evidence-based;
- challenge-specific allowed assistance/scoring policy.

### Acceptance

- no wall-clock dependence;
- same seed + same action trace → same challenge transitions;
- save/checkpoint/replay can reconstruct challenge state from versioned deterministic evidence;
- challenge state cannot issue plant commands.

## M10.9.6.2 — Deterministic external energy-demand profiles

### Deliverables

Introduce versioned deterministic demand profiles suitable for training. Initial profile primitives should remain simple and auditable:

- constant target;
- step change;
- bounded ramp;
- piecewise sequence of constant/ramp segments.

Demand profiles use logical simulation time and publish:

- current external demand;
- next scheduled change when appropriate for the exercise;
- current demand/output error as presentation/evaluation evidence.

### Acceptance

- profile identity is versioned with the exercise/scenario contract;
- demand is unavailable outside exercises that actually own one;
- demand profile never changes generator requested load automatically;
- replay/checkpoint reproduces exactly the same demand timeline.

## M10.9.6.3 — Multidimensional evaluation and scoring contract

### Required dimensions

The first scoring contract should separate at least:

- **SAFETY / PROTECTION DISCIPLINE**;
- **PROCEDURE / REQUIRED ACTIONS**;
- **STABILITY / OPERATING QUALITY**;
- **DEMAND TRACKING** when an energy-demand profile exists;
- **LOGICAL TIME / COMPLETION EFFICIENCY** where the exercise has a time objective.

### Dominance rule

Safety and procedure are dominant dimensions. Good demand tracking or speed must not compensate for an unsafe/prohibited action or a challenge-defined critical procedural failure.

Exact numeric weights/caps are a **design decision to freeze in M10.9.6.3 before implementation**. They must not emerge accidentally from UI code.

### Acceptance

- score is observational and deterministic;
- score cannot change plant/controller/protection state;
- every penalty/reward has a documented evidence source;
- unavailable evidence cannot silently score as success;
- assistance mode and plant-control authority remain separate dimensions and their scoring effects, if any, are explicit.

## M10.9.6.4 — Initial challenge packs

Use existing validated plant/scenario/fault owners only. Initial packs should cover a representative normal-operation set before any accident-gameplay expansion:

1. startup/preparation objective;
2. synchronization and initial loading;
3. bounded power manoeuvring / demand-following;
4. stabilization after a commanded load change;
5. controlled normal shutdown;
6. bounded recovery from an already-supported fault/protection event.

Each pack must declare its objective, demand profile if any, completion/failure conditions and scoring dimensions.

### Non-rule

Do not add a new physical fault merely because a challenge would be more interesting with one. Missing physics goes to the post-M11 backlog.

## M10.9.6.5 — Replay/checkpoint/determinism and closure

### Automated gate

- same seed/action trace reproduces challenge timeline, demand timeline and score exactly;
- checkpoint continuation matches uninterrupted execution;
- assistance-mode change does not alter physical plant state by itself;
- demand never becomes generator load command implicitly;
- protection remains authoritative over challenge success;
- challenge reset/session reset semantics are explicit and deterministic.

### Manual gate

- objective and current demand are understandable;
- demand/requested-load/actual-output are visually distinguishable;
- score decomposition explains why points were gained/lost;
- a protection event cannot look like a successful demand-following result merely because MW error is small.

## Open decisions to settle before coding M10.9.6.3/.4

1. exact score weights/caps and grade scale;
2. whether a protection trip is challenge failure, protected completion or scenario-specific classification — this must be definition-owned, not global;
3. which initial exercises expose the future demand schedule versus only the current demand point;
4. whether assistance mode changes score, and if so by an explicit declared modifier rather than hidden weighting.

## Explicit non-scope

- physical grid dispatch/load coupling driven by the challenge owner;
- new supervisory automation authority;
- severe-accident/damage scoring;
- wall-clock speedrun logic;
- presentation-side scoring calculations.

## Exit condition

M10.9.6 becomes VALIDATED only after build, ordinary suite, focused deterministic challenge/demand/scoring gate and manual exercise confirmation. Only then start M10.9.7.
