The live-workspace implementation should be delivered in bounded slices rather than one large XAML/ViewModel change. These slices are implementation steps inside M10.9.7.3; they do not become separate promoted baselines unless a gate demonstrates a reason to split them.

#### 7.3-A — Workspace identity and shell activation

- add one stable `MissionPerformance` workspace identity;
- register `Mission & Performance` / `MISSION` in `ControlRoomWorkspaceCatalog.Default`;
- preserve all existing workspace identities and the validated COMPUTER F1-F8 page contract;
- extend `MainWindowViewModel` selection/context properties;
- host a dedicated MISSION view in the shell;
- keep navigation selection-only and plant-command-authority free.

Regression contract: exactly one MISSION workspace, no F9, no physical state change when selecting it.

#### 7.3-B — Live projection/publication adapter

Wire the already-validated `MissionPerformanceSnapshotProjector` to the live canonical session evidence. The adapter must consume the same logical-step-aligned lifecycle, demand and scoring owners already qualified before UI activation.

Presentation change detection must be explicit. Generated record equality over snapshots containing `IReadOnlyList<>` is forbidden as a change detector. Prefer a deterministic presentation revision/fingerprint or an explicit field-wise comparer. Tests must cover recreated-but-element-equal lists, list-content changes, scalar changes and unchanged input.

#### 7.3-C — Dedicated MissionPerformance ViewModel

Expose presentation-only properties grouped around objective/lifecycle, demand/request/actual, score dimensions, recent evidence, assistance mode and requested/effective authority. Handle explicitly: no mission, armed, active, completed, failed, demand unavailable, score incomplete and degraded/suspect evidence.

The ViewModel may format labels/units and presentation booleans. It may not recompute score, challenge conditions, protection state or plant control semantics.

#### 7.3-D — Primary UI hierarchy

Use four visual regions:

1. mission/objective and lifecycle strip;
2. three-value demand block (`GRID DEMAND`, `REQUESTED LOAD`, `ACTUAL OUTPUT`);
3. score/classification and dimension decomposition;
4. bounded recent evidence.

Primary safety/protection evidence must remain more prominent than decorative score treatment. Unavailable values must be shown as unavailable, not zero.

#### 7.3-E — Contextual COMPUTER navigation

Add a contextual navigation action to MISSION without altering the F1-F8 page catalog. The navigation target is a workspace selection only; it must not be encoded as `ControlRoomCommand`.

#### 7.3-F — Keyboard/minimum-window contract

MISSION must be reachable and usable without mouse-only actions. Focus order must be deterministic, keyboard focus visible and the primary objective/demand/safety state readable at the minimum supported window size. Scrolling may contain secondary detail but must not hide the at-a-glance mission state.

#### 7.3-G — Focused + manual gate

Automated gate `scripts/run-m10973-mission-performance-live-workspace-audit.cmd` includes workspace registration, no-F9 regression, exact startup pack binding, explicit change-detection semantics, live deterministic demand history, demand/request/actual separation, score-copy fidelity and absence of plant command authority. ## M10.9.7.4 — Deterministic performance timeline and drill-down

Provide a bounded logical-step timeline for mission events such as:

- objective/phase transition;
- demand change;
- key operator action;
- protection/alarm event relevant to scoring;
- score-dimension change;
- challenge completion/failure/protected-boundary classification.

Timeline ordering must reuse deterministic logical step/event sequence semantics. Wall clock may be displayed only as non-authoritative session metadata if already available; it may not order or score events.

Drill-down may navigate to the relevant subsystem schematic, command consequence or existing alarm/log evidence without mutating plant state.

### Detailed implementation slices for M10.9.7.4

#### 7.4-A — Timeline projection contract

Create a bounded Application read model over canonical recorder/challenge evidence. Stable order is logical step first, canonical source sequence second, with stable event/source tie-breakers only when required. The timeline is not a second recorder.

#### 7.4-B — Timeline presentation

Show logical step/time, category, concise evidence summary and optional score/source context. Distinguish objective, operator action, protection and scoring evidence visually and textually.

#### 7.4-C — Drill-down target contract

Timeline rows may carry presentation navigation targets to subsystem workspaces, alarms/events or COMPUTER consequence/context evidence. Missing targets degrade to generic evidence rather than failing or issuing a command.

#### 7.4-D — Replay/checkpoint equivalence

Qualify uninterrupted vs replay, checkpoint seek/resume, terminal-challenge/continuing-plant behavior, duplicate suppression and bounded last-N identity.

#### 7.4-E — Gate

Automated timeline/replay/navigation assertions plus a manual drill-down/back-navigation review.

- no active mission;
