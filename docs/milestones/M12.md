# M12 — Extreme Operations Foundations — DETAILED PLAN

**Strategic epic:** Epic A — Extreme Operations & Accident Progression, foundation phase.  
**Status:** PLANNED — starts only after M11 release hardening is explicitly closed.  
**Detailed cross-milestone execution map:** [`../FORWARD_EXECUTION_PLAN_M10_9_7_TO_M15.md`](../FORWARD_EXECUTION_PLAN_M10_9_7_TO_M15.md).

## Goal

Make the plant model intentionally robust and explicit at extreme/off-design states before granting broader accident/fault authority. M12 establishes physical support boundaries, credible post-trip heat ownership, persistent integrity primitives and incident-state persistence. It does **not** yet authorize severe consequence claims.

## Governing rules

1. no extreme-condition support is claimed until a focused test demonstrates it;
2. unsupported states fail explicitly rather than being hidden by global clamps;
3. directionality belongs to the owning component/connection, not to a global solver rule;
4. post-trip decay heat is physical energy, not a scenario flag;
5. functional equipment state and physical integrity are separate;
6. alarm priority and physical incident severity are separate;
7. all new persistent physical state must be deterministic, replayable and checkpoint-compatible;
8. M12 introduces foundations, not leaks/ruptures/fires/core damage.

## Explicit non-scope

M12 does not add:

- scripted leaks/ruptures/fires;
- severe core-damage progression;
- UI-owned physics;
- arbitrary protections whose only purpose is to keep numerics comfortable;
- global reverse-flow clamps;
- generic `fault => damaged` mappings;
- automatic repair on protection reset/alarm acknowledge;
- instructor shortcuts that bypass physical owners.

## M12.1 — Flow-owner directionality and support inventory

### Purpose

Create a complete, executable statement of which modeled paths can reverse flow, which cannot, and why.

### Inventory scope

Audit every component that owns or constrains mass/energy flow, including at least:

- primary-circuit pipes and branches;
- reactor/fuel-channel group paths;
- main-circulation pumps and pump branches;
- headers and steam-drum transfer paths;
- steam-drum steam sources;
- main-steam lines;
- stop, control, bypass and relief valves;
- turbine stage-group flow paths;
- condenser/hotwell paths;
- condensate/feedwater pumps and return paths;
- grid/electrical signed power exchange where directionality is relevant;
- existing external source/sink boundaries;
- currently modeled fault-created source/sink paths.

### Required classification

Every row must freeze one semantic:

```text
BIDIRECTIONAL
ONE_WAY_BY_PHYSICS
ONE_WAY_BY_EXPLICIT_DEVICE
UNSUPPORTED_OUTSIDE_CURRENT_ENVELOPE
```

The evidence record should state:

- component/connection ID/type;
- state owner;
- sign convention;
- whether negative flow is physically meaningful;
- reverse-driving-pressure behavior;
- associated valve/check/isolation owner if any;
- unsupported conditions;
- focused regression method(s).

### Implementation work

- add missing definition-level directionality semantics only where the current model is ambiguous;
- remove accidental one-way assumptions that are not physically owned;
- keep one-way behavior local to the component/device that owns it;
- preserve signed mass/energy accounting across reverse-capable paths;
- do not add a global solver clamp.

### Focused tests

For each class of owner:

- positive driving condition;
- near-zero driving condition;
- reversed driving condition;
- explicit one-way-device blocking where applicable;
- unknown/unsupported envelope fail-closed case;
- conservation sign convention.

### Evidence

Produce a machine-readable directionality matrix plus a human-readable summary. The matrix becomes a prerequisite for M15 leak/rupture work.

### Exit condition

No flow-owning component remains semantically “unknown”; every owner is either supported in a declared directionality mode or explicitly unsupported.

## M12.2 — Extreme-state validation matrix

### Purpose

Determine the real envelope of the current model before expanding fault authority.

### State families

Construct deliberate test points/trajectories around:

- near-empty but nonnegative fluid inventory;
- very high but representable inventory/fill where meaningful;
- low absolute pressure above valid model floor;
- high pressure within supported property/domain limits;
- low/high temperature within supported water/steam correlations;
- high void / low liquid fraction;
- saturated/two-phase boundary approaches;
- near-zero flow;
- supported reverse flow;
- high supported flow;
- pump coastdown/stall-like low-flow states where currently represented;
- post-trip cooling/depressurization trajectories;
- condenser vacuum degradation boundaries;
- steam admission/load-rejection extremes currently reachable by canonical commands.

### Classification per case

Each matrix cell must be one of:

```text
SUPPORTED_BOUNDED
SUPPORTED_REDUCED_FIDELITY
SUPPORTED_WITH_EXPLICIT_PROTECTION_BOUNDARY
UNSUPPORTED_FAIL_CLOSED
```

### Required evidence

Where applicable record:

- minimum/maximum inventory;
- pressure/temperature envelope;
- conservation residuals;
- finite-state/quantity checks;
- convergence outcome;
- protection/fault involvement;
- exact failure type/message for unsupported cases;
- deterministic repeat result.

### Numerical discipline

A failure discovered here does not authorize arbitrary retuning. First classify it as:

- invalid physical input;
- missing component semantics;
- property-model domain gap;
- solver robustness problem;
- genuinely unsupported phenomenon.

Only then scope a fix.

### Exit condition

Known extreme-state support is explicit enough that M15 cannot accidentally rely on a state the plant model cannot represent.

## M12.3 — Full-plant post-trip decay-heat ownership

### Purpose

Make residual reactor heat after fission shutdown part of the full-plant thermal trajectory, not merely an isolated kinetics datum.

### Audit first

Trace current decay heat through:

```text
reactor power history
→ decay-heat state
→ core/fuel thermal owner
→ coolant heat transfer
→ primary inventory/steam generation
→ secondary/condenser heat rejection where modeled
```

Identify any discontinuity where decay heat exists numerically but is not carried through the integrated runtime.

### Required implementation semantics

- decay heat remains history-dependent;
- fission/prompt thermal power and decay heat remain separately observable;
- scram/trip does not zero residual heat;
- energy enters the same canonical thermal accounting used by the plant;
- no scenario-specific residual-heat flag;
- checkpoint/replay reconstructs the exact decay-heat state from canonical evidence/state.

### Reference trajectories

Qualify at least:

- trip from normal 5 MWe-equivalent operation;
- trip from sustained high-load/10 MWe operation where supported;
- trip after shorter/longer prior operation so history dependence is visible;
- continued adequate cooling;
- reduced but still supported cooling;
- recovery/restart only where current physics actually supports it.

### Evidence

Record post-trip fission power, decay heat, core thermal state, primary heat removal and relevant secondary heat rejection over logical time.

### Non-scope

No fuel-damage threshold, dryout damage or severe-accident severity classification is introduced here.

### Exit condition

A post-trip thermal trajectory is physically owned end-to-end and is deterministic across replay/checkpoint.

## M12.4 — Persistent component integrity/stress primitives

### Purpose

Create the state seam M15 will later use for real damage without conflating `TRIPPED`, `CLOSED`, `FAILED` and `DAMAGED`.

### State separation

Freeze three concepts:

1. **functional/effective state** — what the component is doing now;
2. **physical integrity state** — whether the component remains physically capable/intact;
3. **exposure/stress evidence** — deterministic accumulated physical burden.

### Candidate integrity vocabulary

The exact enum is not frozen until design review, but a likely progression is:

```text
HEALTHY
STRESSED
DEGRADED
DAMAGED
FAILED
DESTROYED
```

Fewer states are preferable if the model cannot justify the distinctions.

### Candidate exposure channels

Introduce only those backed by an owning model, such as:

- pressure over-limit exposure;
- temperature over-limit exposure;
- overspeed exposure;
- dry-running/cavitation-like exposure if modeled;
- electrical/thermal overload exposure if modeled;
- uncovery/overtemperature exposure later consumed by M15 core damage.

### Determinism requirements

- fixed-step accumulation;
- no wall-clock time;
- canonical units;
- explicit reset semantics (normally no operator reset);
- checkpoint/replay exactness;
- session archive compatibility/versioning if state becomes persisted.

### Tests

- exposure accumulates only under owning condition;
- recovery below threshold behaves as specified (hold, decay, or irreversible) and is explicit;
- alarm acknowledgement does not alter integrity;
- protection reset does not heal integrity;
- functional trip does not automatically imply damage;
- damage can persist while a command/control state changes.

### Exit condition

At least one representative component family proves the generic seam without yet introducing broad consequence behavior.

## M12.5 — Physical IncidentSeverity and persistence scaffolding

### Purpose

Represent physical consequence seriousness separately from operator alarm priority.

### Contract

`IncidentSeverity` is observational/derived from modeled physical state and may consume:

- integrity loss;
- persistent leak/fire/damage states once those exist;
- affected-system importance;
- persistence/duration where physically justified;
- consequence magnitude.

It must **not** be derived simply from:

- alarm priority;
- challenge score;
- scenario name;
- Instructor/Fault selection.

### Initial M12 behavior

Because M12 does not yet add major consequence families, the severity model may mostly remain `NONE`/foundation states. The important result is the ownership/persistence contract.

### Integration

Expose severity to:

- canonical presentation snapshots;
- recorder/checkpoint/session state if persistent owner requires it;
- post-incident analysis;
- later M13 Instructor presentation;
- later M15 consequence scoring/summary only as evidence, not as challenge authority.

### Tests

- critical alarm with successful protection and no damage does not automatically imply severe incident;
- persistent integrity loss survives alarm reset;
- replay/checkpoint/session reconstruction preserves severity inputs/output.

### Exit condition

Physical severity exists as a separate deterministic axis with no command/protection authority.

## M12.6 — Extreme-foundation closure

### Automated closure matrix

Require green gates for:

- directionality inventory;
- extreme-state matrix;
- full-plant decay heat;
- integrity/stress semantics;
- incident severity;
- replay/checkpoint/session reconstruction;
- ordinary suite;
- selected long trajectories where new persistent thermal/integrity state warrants it.

### Manual/engineering review

Review `KNOWN_MODEL_LIMITATIONS.md` and explicitly list:

- unsupported reverse-flow cases;
- unsupported extreme property states;
- reduced-fidelity extreme-state regions;
- damage/consequence mechanisms still absent.

### Exit condition

M12 closes the **foundations only**. Leak, rupture, fire, mechanical/electrical failure and severe core-damage mechanisms remain M15 work and each requires its own explicit causal model.
