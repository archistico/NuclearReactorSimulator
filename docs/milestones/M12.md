# M12 — Extreme Operations Foundations — DETAILED PLAN

**Strategic epic:** Epic A — Extreme Operations & Accident Progression, foundation phase.  
**Status:** PLANNED — starts only after M11 release hardening is explicitly closed.  
**Detailed cross-milestone execution map:** [`../FORWARD_EXECUTION_PLAN_M10_9_7_TO_M15.md`](../FORWARD_EXECUTION_PLAN_M10_9_7_TO_M15.md).  
**Numerical review disposition:** [`../SIMULATION_NUMERICAL_REGULARITY_AND_RUNTIME_REVIEW.md`](../SIMULATION_NUMERICAL_REGULARITY_AND_RUNTIME_REVIEW.md).

**Cross-milestone execution discipline:** [`../POST_M10_TO_M15_EXECUTION_MASTER_PLAN.md`](../POST_M10_TO_M15_EXECUTION_MASTER_PLAN.md) and [`../CHANGE_IMPACT_REVALIDATION_POLICY.md`](../CHANGE_IMPACT_REVALIDATION_POLICY.md).

## Goal

Make the plant model intentionally robust and explicit at extreme/off-design states before granting broader accident/fault authority. M12 establishes directionality, near-zero/numerical support boundaries, complete pump-energy ownership, credible post-trip heat ownership, persistent integrity primitives and incident-state persistence. It does **not** yet authorize severe consequence claims.

## Governing rules

1. no extreme-condition support is claimed until a focused test demonstrates it;
2. unsupported states fail explicitly rather than being hidden by global clamps;
3. directionality belongs to the owning component/connection, not to a global solver rule;
4. numerical smoothing is never introduced merely to make Newton converge;
5. a constitutive-law change requires before/after physical, conservation, replay and long-horizon evidence;
6. post-trip decay heat is physical energy, not a scenario flag;
7. pump shaft/electrical/thermal loss ownership must be explicit before stronger full-plant energy claims;
8. functional equipment state and physical integrity are separate;
9. alarm priority and physical incident severity are separate;
10. all new persistent physical state must be deterministic, replayable and checkpoint-compatible;
11. M12 introduces foundations, not leaks/ruptures/fires/core damage.

## Explicit non-scope

M12 does not add:

- scripted leaks/ruptures/fires;
- severe core-damage progression;
- UI-owned physics;
- arbitrary protections whose only purpose is to keep numerics comfortable;
- global reverse-flow clamps;
- speculative hydraulic epsilon/deadband/leakage constants without evidence;
- generic `fault => damaged` mappings;
- automatic repair on protection reset/alarm acknowledge;
- instructor shortcuts that bypass physical owners.

## M12.0 — Reference Operating-Point Equilibrium & Stability Qualification

### Purpose

Before changing extreme-state constitutive laws, establish whether the current normal reference points are genuine bounded operating points of the canonical 10 ms coupled runtime or merely short-horizon trajectories with slow redistribution.

Detailed design: [`../REFERENCE_OPERATING_POINT_EQUILIBRIUM_AND_STABILITY_PLAN.md`](../REFERENCE_OPERATING_POINT_EQUILIBRIUM_AND_STABILITY_PLAN.md).

### Execution slices

1. **M12.0.1 residual taxonomy / participation registry** — freeze `STATIONARY_REQUIRED | BOUNDED_PERIODIC | SLOW_EVOLUTION | CYCLIC_COORDINATE | BOOKKEEPING_EXCLUDED`, metric IDs, units and source owners.
2. **M12.0.2 closed-loop residual inspector** — read-only Application validation tooling over consecutive canonical committed states; no correction and no second integrator.
3. **M12.0.3 domain-headroom / trend diagnostics** — window slopes and canonical-resolver directional support probes; no duplicated thermodynamic equations.
4. **M12.0.4 fixed-input plant-hold seam** — only the minimum validation-only composition required to separate authored physical-seed imbalance from controller compensation.
5. **M12.0.5 bounded operating-point trimmer, if needed** — trim only allow-listed initial-condition/control-memory values; never model coefficients, protection thresholds or test tolerances.
6. **M12.0.6 perturbation stability / closure** — small deterministic disturbances, convergence/return evidence, exact-version implications and long-horizon requalification.

### Exact-version rule

A changed production operating-point seed is a new exact identity. Existing `integrated-operations-desktop-stable@4` remains immutable. The plan provisionally reserves `@5` for a future repaired seed if evidence proves one is required; no version is created merely by writing this plan.

### Exit condition

M12.0 closes only when normal reference-point behavior is explicitly classified and its residual/stability evidence is reproducible. It may close **without** a trimmer if existing authored states prove adequate. M12.1+ may not use equilibrium tooling as a hidden correction mechanism.

## M12.1 — Flow-owner directionality and support inventory

### Purpose

Create a complete, executable statement of which modeled paths can reverse flow, which cannot, and why.

### Inventory scope

Audit every component that owns or constrains mass/energy flow, including at least:

- primary-circuit pipes and branches;
- reactor/fuel-channel group paths;
- main-circulation pumps and pump branches;
- headers and steam-drum transfer paths;
- steam-drum steam sources;
- main-steam lines;
- stop, control, bypass and relief valves;
- turbine stage-group flow paths;
- condenser/hotwell paths;
- condensate/feedwater pumps and return paths;
- grid/electrical signed power exchange where directionality is relevant;
- existing external source/sink boundaries;
- currently modeled fault-created source/sink paths.

### Required classification

Every row must freeze one semantic:

```text
BIDIRECTIONAL
ONE_WAY_BY_PHYSICS
ONE_WAY_BY_EXPLICIT_DEVICE
UNSUPPORTED_OUTSIDE_CURRENT_ENVELOPE
```

The evidence record states:

- component/connection ID/type;
- state owner;
- sign convention;
- whether negative flow is physically meaningful;
- reverse-driving-pressure behavior;
- associated valve/check/isolation owner if any;
- unsupported conditions;
- focused regression method(s).

### Check-valve clarification

The current pump discharge check is an explicit one-way device. The current blocked map is continuous at zero flow but non-smooth. Do not reclassify that as a mathematical discontinuity and do not invent reverse leakage merely to smooth a solver. Any finite leakage law requires a physically owned component model and M12.2 evidence.

### Implementation work

- add missing definition-level directionality semantics only where the current model is ambiguous;
- remove accidental one-way assumptions that are not physically owned;
- keep one-way behavior local to the component/device that owns it;
- preserve signed mass/energy accounting across reverse-capable paths;
- do not add a global solver clamp.

### Focused tests

For each class of owner:

- positive driving condition;
- near-zero driving condition;
- reversed driving condition;
- explicit one-way-device blocking where applicable;
- unknown/unsupported envelope fail-closed case;
- conservation sign convention.

### Evidence and exit

Produce a machine-readable directionality matrix plus a human-readable summary. No flow-owning component remains semantically unknown. This matrix is a prerequisite for M12.2/M12.3 and M15 leak/rupture work.

## M12.2 — Near-zero hydraulic constitutive regularity and conditioning audit

### Purpose

Measure and classify the non-smooth/numerically stiff regions of the already validated hydraulic/thermodynamic map **before** changing any constitutive law or corrector policy.

### Frozen subjects

Audit at least:

1. passive quadratic inverse flow `m_dot = sign(Δp) * sqrt(|Δp|/R)` as `Δp → 0`;
2. pump discharge check-valve transition at raw reverse flow → zero blocked flow;
3. valve effective resistance as flow coefficient approaches zero and quick-opening characteristic near closed position;
4. H.9 normalized coordinate/residual scales and finite-difference probes around reversals;
5. `JacobianDiagonalRegularization` in normalized space;
6. pivot-spread heuristic currently exposed as `MaximumPivotConditionEstimate`/estimate evidence;
7. deterministic compensated summation order for mixed-sign source terms;
8. conditional bounded previous-phase thermodynamic continuity versus the memoryless base resolver at corrected trigger points.

### Phase A — observational census

Build frozen probes across representative paths and profiles:

- `Δp` sweeps through zero from both directions;
- finite-difference perturbations that remain on one side versus cross zero;
- exact-zero/reverse check-valve cases;
- valve exact closed and small-open states within the supported actuator envelope;
- trigger/non-trigger four-node states from historical H/I provenance;
- repaired exact @4 reference states plus selected historical exact-version controls.

Record:

- flow/output continuity;
- local finite-difference slope estimates;
- normalized coordinate/residual scales;
- Jacobian dimension and probe side;
- pivot spread and any stronger diagnostic evaluated observationally;
- line-search/probe infeasibility counts;
- corrected-path trigger/commit/rollback outcome;
- conservation residuals and deterministic fingerprints.

### Phase B — candidate comparison, still non-production

Only after the census may observational candidates be compared, such as:

- a physically justified near-zero transition law;
- alternative finite-difference probe placement;
- normalized relative diagonal regularization;
- stronger deterministic conditioning diagnostics;
- alternative deterministic compensated-sum ordering.

No candidate is presumed correct in advance. A centered difference alone does not remove a constitutive singularity. A reverse-leakage resistance is not accepted merely because it is numerically smooth.

### Production-change gate

Any production change must demonstrate:

- continuity/regularity improvement on the targeted evidence;
- no new conservation/ownership residual;
- unchanged unsupported-state fail-closed behavior;
- replay/checkpoint deterministic repeat;
- affected H/I reference trajectory requalification;
- exact-version compatibility preserved or deliberately versioned;
- bounded performance cost.

If current behavior proves adequate inside the supported envelope, M12.2 may close with **no production change**.

### Branch-continuity decision

The base `SimplifiedWaterSteamThermodynamicModel` remains memoryless. The validated corrected four-node path may apply bounded previous-phase continuity and commit that corrected candidate when authority permits. Unifying or retiring these semantics is a separate M12.2 decision requiring evidence; it is not a documentation cleanup.

### Exit condition

Every identified near-zero/non-smooth/conditioning mechanism has a measured support statement and either a validated correction or an explicit retained limitation.

## M12.3 — Extreme-state validation matrix

### Purpose

Determine the real physical/property-model envelope before expanding fault authority.

### State families

Construct deliberate test points/trajectories around:

- near-empty but nonnegative fluid inventory;
- very high but representable inventory/fill where meaningful;
- low absolute pressure above valid model floor;
- high pressure within supported property/domain limits;
- low/high temperature within supported water/steam correlations;
- high void / low liquid fraction;
- saturated/two-phase boundary approaches;
- near-zero flow using the M12.2 support statement;
- supported reverse flow;
- high supported flow;
- pump coastdown/stall-like low-flow states where currently represented;
- post-trip cooling/depressurization trajectories;
- condenser vacuum degradation boundaries;
- steam admission/load-rejection extremes currently reachable by canonical commands.

### Classification per case

Each matrix cell is one of:

```text
SUPPORTED_BOUNDED
SUPPORTED_REDUCED_FIDELITY
SUPPORTED_WITH_EXPLICIT_PROTECTION_BOUNDARY
UNSUPPORTED_FAIL_CLOSED
```

### Required evidence

Where applicable record:

- minimum/maximum inventory;
- pressure/temperature envelope;
- conservation residuals;
- finite-state/quantity checks;
- convergence outcome;
- protection/fault involvement;
- exact failure type/message for unsupported cases;
- deterministic repeat result.

### Numerical discipline

A failure discovered here does not authorize arbitrary retuning. First classify it as invalid physical input, missing component semantics, property-model domain gap, solver robustness problem, or genuinely unsupported phenomenon. Then scope the owner.

### Exit condition

Known extreme-state support is explicit enough that M15 cannot accidentally rely on a state the plant model cannot represent.

## M12.4 — Pump mechanical / electrical / thermal energy ownership closure

### Purpose

Close the deliberately reduced M1.5 ownership gap before stronger full-plant conservation and accident-energy claims.

### Current boundary

The current pump model:

- exchanges hydraulic power with the fluid;
- reports positive shaft demand from hydraulic power and efficiency;
- deliberately does not yet model motor/electrical dynamics or deposit inefficiency as component/fluid/ambient heat.

M12.4 must turn this from historical non-scope into an explicit integrated ownership decision.

### Required ownership questions

For each modeled pump family determine:

- which shaft/motor/electrical owner supplies positive shaft demand;
- whether current electrical station-service modeling can own that draw or requires a new bounded owner;
- where `(shaft input - hydraulic output)` is deposited when loss-to-heat is modeled;
- whether the loss heats fluid, pump/component thermal mass, ambient sink, or a documented split;
- behavior at zero flow, blocked discharge, stopped rotor and supported reverse-flow states;
- whether any thermal/integrity state becomes persistent.

### Required evidence

- pump hydraulic power;
- shaft demand;
- electrical/mechanical supply where modeled;
- modeled loss heat;
- endpoint fluid-energy balances;
- whole-plant ownership residual;
- deterministic replay/checkpoint evidence;
- no accidental regenerative generation unless explicitly modeled.

### Non-scope

Do not add cavitation, detailed motor electromagnetic transients or failure/damage merely to close accounting. Those require their own owners and later milestones.

### Exit condition

There is no unowned modeled pump-energy term inside the supported M12 envelope, or any intentionally omitted term is explicitly classified and excluded from later accident claims.

## M12.5 — Full-plant post-trip decay-heat ownership

### Purpose

Make residual reactor heat after fission shutdown part of the full-plant thermal trajectory, not merely an isolated kinetics datum.

### Audit first

Trace current decay heat through:

```text
reactor power history
→ decay-heat state
→ core/fuel thermal owner
→ coolant heat transfer
→ primary inventory/steam generation
→ secondary/condenser heat rejection where modeled
```

Identify any discontinuity where decay heat exists numerically but is not carried through the integrated runtime.

### Required implementation semantics

- decay heat remains history-dependent;
- fission/prompt thermal power and decay heat remain separately observable;
- scram/trip does not zero residual heat;
- energy enters the same canonical thermal accounting used by the plant;
- no scenario-specific residual-heat flag;
- checkpoint/replay reconstructs the exact decay-heat state from canonical evidence/state.

### Reference trajectories

Qualify at least:

- trip from normal 5 MWe-equivalent operation;
- trip from sustained high-load/10 MWe operation where supported;
- trip after shorter/longer prior operation so history dependence is visible;
- continued adequate cooling;
- reduced but still supported cooling;
- recovery/restart only where current physics actually supports it.

### Evidence and non-scope

Record post-trip fission power, decay heat, core thermal state, primary heat removal and relevant secondary heat rejection over logical time. No fuel-damage threshold, dryout damage or severe-accident severity classification is introduced here.

### Exit condition

A post-trip thermal trajectory is physically owned end-to-end and deterministic across replay/checkpoint.

## M12.6 — Persistent component integrity/stress primitives

### Purpose

Create the state seam M15 will later use for real damage without conflating `TRIPPED`, `CLOSED`, `FAILED` and `DAMAGED`.

### State separation

Freeze three concepts:

1. **functional/effective state** — what the component is doing now;
2. **physical integrity state** — whether the component remains physically capable/intact;
3. **exposure/stress evidence** — deterministic accumulated physical burden.

### Candidate integrity vocabulary

The exact enum is not frozen until design review, but a likely progression is:

```text
HEALTHY
STRESSED
DEGRADED
DAMAGED
FAILED
DESTROYED
```

Fewer states are preferable if the model cannot justify the distinctions.

### Candidate exposure channels

Introduce only those backed by an owning model, such as:

- pressure over-limit exposure;
- temperature over-limit exposure;
- overspeed exposure;
- dry-running/cavitation-like exposure if modeled;
- electrical/thermal overload exposure if modeled;
- uncovery/overtemperature exposure later consumed by M15 core damage.

### Determinism requirements

- fixed-step accumulation;
- no wall-clock time;
- canonical units;
- explicit reset semantics (normally no operator reset);
- checkpoint/replay exactness;
- session archive compatibility/versioning if state becomes persisted.

### Tests and exit

Verify that exposure accumulates only under the owning condition, recovery semantics are explicit, alarm acknowledgement/protection reset do not heal integrity, functional trips do not imply damage, and damage can persist through command-state changes. At least one representative component family must prove the generic seam without yet introducing broad consequence behavior.

## M12.7 — Physical IncidentSeverity and persistence scaffolding

### Purpose

Represent physical consequence seriousness separately from operator alarm priority.

### Contract

`IncidentSeverity` is observational/derived from modeled physical state and may consume:

- integrity loss;
- persistent leak/fire/damage states once those exist;
- affected-system importance;
- persistence/duration where physically justified;
- consequence magnitude.

It must **not** be derived simply from alarm priority, challenge score, scenario name or Instructor/Fault selection.

### Initial M12 behavior

Because M12 does not yet add major consequence families, the severity model may mostly remain `NONE`/foundation states. The important result is the ownership/persistence contract.

### Integration and tests

Expose severity to canonical presentation snapshots, recorder/checkpoint/session state if required, post-incident analysis, later M13 Instructor presentation and later M15 consequence summaries. Critical alarm without physical damage must not automatically imply severe incident; persistent integrity loss must survive alarm reset; replay/checkpoint/session reconstruction must preserve severity inputs/output.

### Exit condition

Physical severity exists as a separate deterministic axis with no command/protection authority.
