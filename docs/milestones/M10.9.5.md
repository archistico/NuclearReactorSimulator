# M10.9.5 — Contextual Command Consequence Model — PLAN

**Status:** IN PROGRESS — Phase I is closed; M10.9.5.1 and M10.9.5.2 are VALIDATED; M10.9.5.3 is the active candidate.

## Goal

Turn the existing contextual command list into an operator-explanation surface that answers five separate questions without becoming a second physics/control owner:

1. **Direct effect** — what accepted command/actuator intent is being requested now?
2. **Expected downstream influence** — what existing plant/controller/topology relationships make this command relevant?
3. **Permissives/blockers** — what currently published authority/availability state prevents or conditions dispatch?
4. **What to monitor** — which already-published measurements/states should the operator watch?
5. **Observed response** — what actually changed after dispatch?

Expected influence and observed response must remain visibly and structurally distinct.

## Architectural invariants

- command dispatch remains `ControlRoomCommand` → `IControlRoomCommandDispatcher` → canonical runtime/scenario validation;
- the consequence model never writes Simulation state;
- the consequence model never predicts pressure, temperature, power, flow or reactivity numerically;
- AVAILABLE/BLOCKED/UNAVAILABLE remains advisory presentation state, not a new permissive owner;
- protection/interlock truth remains M5/canonical-owner truth;
- consequence chains use explicit authored relationships; there is no unconstrained automatic graph traversal that can invent causality;
- unavailable model/measurement data remains unavailable;
- replay records commands and actual state as today; consequence presentation is derivable evidence, not new physical state.

## M10.9.5.1 — Consequence semantics and catalog

**Current candidate contract:** cover all 27 current `ControlRoomCommandKind` values with deterministic authored semantics. Commands currently supported by the runtime but not yet exposed by the M10.4 COMMANDS console (the five turbine-valve/control-valve commands) are still catalogued so future UI exposure cannot silently bypass consequence semantics.

Unsupported/future command-target shapes must resolve to explicit `NO AUTHORED CONSEQUENCE MAP`; the catalog must never infer a causal relationship from an unknown enum/target combination.

### Deliverables

Define a stable consequence vocabulary for every currently exposed command family:

- command identity and canonical target;
- direct accepted intent/effective-action description;
- zero or more explicit expected-influence entries;
- current blocker/permissive references when already published;
- monitor targets with MEASURED/MODEL/state provenance;
- explicit `NO AUTHORED CONSEQUENCE MAP` state when a defensible relationship is not yet available.

Expected-influence entries must be qualitative and topology/control based. Allowed semantics should be frozen before implementation, for example:

- `INCREASES EXPECTED DEMAND ON`;
- `DECREASES EXPECTED DEMAND ON`;
- `ENABLES / DISABLES PATH`;
- `AFFECTS / MAY AFFECT` when sign is not defensible;
- `PROTECTION MAY OVERRIDE`;
- `MONITOR`.

Do not infer confidence percentages or quantitative future values.

### Acceptance

- every current command kind/target is either mapped or explicitly unmapped;
- every referenced target/instrument/schematic node resolves to a canonical published identifier;
- no new physics/control/protection owner is introduced;
- catalog order and content are deterministic for the same snapshot.

## M10.9.5.2 — Explicit dependency-chain projection

**Current candidate contract:** build deterministic authored bounded chains over the validated M10.9.5.1 semantics. Whole-plant mimic element/connection IDs and published snapshot paths are the only static topology references; no arbitrary graph traversal is permitted.

### Deliverables

Project authored chains of the form:

```text
COMMAND INTENT
   ↓
ACTUATOR / CONTROLLER / BREAKER TARGET
   ↓
EXISTING PHYSICAL OR CONTROL PATH
   ↓
MONITOR SIGNAL(S)
   ↓
PROTECTION / ALARM RELATION WHEN RELEVANT
```

The chain is catalog-authored and bounded. Do not compute arbitrary shortest paths through the plant graph.

Each chain element must identify whether it represents:

- command intent;
- control/actuator state;
- physical process path;
- measurement/model observation;
- protection/alarm relation.

### Acceptance

- chain endpoints exist in current mimic/schematic contracts;
- no hidden UI-only plant topology is created;
- the same command/target/snapshot yields the same chain and ordering;
- selection/highlight data is presentation-only and has no runtime side effect.

## M10.9.5.3 — COMMANDS, context inspector and schematic integration

**Current candidate contract (Hotfix 2):** integrate the validated M10.9.5.1 consequence semantics and M10.9.5.2 dependency chains into the existing F4 COMMANDS workstation. The first build's ViewModel API-name mismatch was fixed by Hotfix 1; the subsequent ordinary suite exposed only a stale XAML-test expectation for an intentional `Mode=OneWay` focus binding. Hotfix 2 aligns that contract and makes visual focus exact: element references highlight directly, connection references use a declared source-element proxy, and non-graphical references produce no highlight. Selection remains presentation-only and no second topology is created.

### Deliverables

For the focused command, present in progressive disclosure:

1. command + target;
2. current AVAILABLE/BLOCKED/UNAVAILABLE state and reason;
3. direct effect;
4. expected influence;
5. what to monitor;
6. a selectable dependency-chain highlight on the relevant full-plant mimic/subsystem schematic.

Blocked commands remain inspectable but not dispatchable.

### Acceptance

Manual checklist: [`../M10_9_5_3_MANUAL_VALIDATION_CHECKLIST.md`](../M10_9_5_3_MANUAL_VALIDATION_CHECKLIST.md).

- keyboard selection works without dispatch until explicit Enter/execute;
- dependency highlighting never changes plant state;
- unavailable/non-graphical evidence is labelled and clears the mimic highlight rather than fabricating a target;
- minimum supported window remains usable;
- existing M10.4 command feedback remains intact.

## M10.9.5.4 — Observed response

### Rule

Observed response is **evidence after the command**, not a declaration that the command caused every change.

### Deliverables

After an accepted dispatch, show a deterministic bounded observation of the command's authored monitor set using logical simulation steps. At minimum expose:

- value/state at dispatch boundary;
- latest observed value/state;
- actual delta/direction when meaningful;
- command accepted/rejected feedback;
- protection/interlock override if observed.

The first version must not invent a generic `SUCCESS/FAILURE` from numeric deltas unless an existing canonical command/procedure contract already defines success.

### Acceptance

- observation windows use logical steps only, never wall-clock time;
- replay of the same command trace reconstructs the same observed-response presentation;
- unrelated state changes are not labelled as proven causal consequences;
- rejected commands do not display fictional plant effects.

## M10.9.5.5 — Closure gate

### Automated gate

Must cover:

- catalog completeness / explicit-unmapped semantics;
- valid canonical identifiers;
- deterministic consequence projection;
- AVAILABLE/BLOCKED/UNAVAILABLE preservation;
- expected-vs-observed separation;
- schematic highlight integrity;
- replay determinism;
- no plant-state change caused by inspection/navigation alone;
- regression of existing command dispatch/protection tests.

### Manual HMI gate

Check representative reactor, primary, turbine, generator/breaker, alarm and runtime commands:

- explanation is understandable without reading code;
- direct effect is not confused with expected influence;
- expected influence is not presented as prediction;
- blockers/permissives are clearly current-state evidence;
- monitor list leads to useful instruments/schematics;
- observed response is visibly post-command evidence;
- keyboard-only operation remains practical.

## Explicit non-scope

M10.9.5 does not add:

- numerical predictive simulation in Application/Avalonia;
- new physical/control/protection commands;
- free-form or natural-language command parsing;
- automatic execution of dependency chains;
- challenge timing, grid demand or scoring;
- component damage/incident progression;
- new plant physics requested only to make a consequence diagram richer.

## Exit condition

M10.9.5 becomes VALIDATED only after explicit local build, complete ordinary tests, focused consequence-model gate and manual HMI confirmation. Only then start M10.9.6.
